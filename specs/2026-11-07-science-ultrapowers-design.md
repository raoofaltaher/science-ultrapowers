# science-ultrapowers: the research-lab methodology as a Claude Code plugin

Status: approved 2026-11-07. Ticket: none.

## Intent

The owner runs doctoral research as a simulated research group: fourteen AI roles (project manager, academic supervisor, three researchers, experiments lead, findings curator, two writers, two reviewers, citation auditor, research engineer, decision-systems specialist) plus the owner as the human References & Resources Specialist, bound by stage gates G0-G6 and a non-negotiable evidence rule. Today that lab lives in Claude Science (15 profiles, published skills, an artifact store with lineage, a memory pool) and in a hand-installed copy for Claude Code (`research_lab/claude_code_team/`). Claude Science is in beta and limits the work; Claude Code is where the lab should run from now on.

The moment this exists for: the owner opens Claude Code in a research project, old or new, says "lab, where do we stand?", and the whole team, its rules, its records, its artifacts and its memory are there. For the source project in particular, the lab continues from the exact state Claude Science left: the same 79 memories, the same 418 artifacts with their 555 versions and 940 dependency edges, the same 1,527 reviewer verdicts, the same profiles.

Success looks like: one `/plugin marketplace add raoofaltaher/science-ultrapowers` and one `/plugin install science-ultrapowers@science-ultrapowers`, then `initializing-a-research-lab` in any project folder, and the lab works the way the Claude Science lab worked, with git holding everything.

## Goals, non-goals and anti-goals

Goals: what must be true when this ships.

- G1. A Claude Code plugin and marketplace, in one repository, built from a clone of `obra/superpowers` v7.0.2 with its git history removed and re-initialised as `raoofaltaher/science-ultrapowers` (public).
- G2. Only the Claude Code harness remains: every other harness's manifest, hook variant, tool-mapping reference, install doc and test is removed.
- G3. The lab's six skills are rewritten in the superpowers form (frontmatter "Use when…" descriptions, overview with core principle, Iron Law and rationalization tables for discipline skills, quick-reference tables for reference skills, "your human partner" vocabulary, actions not tool names) and renamed verb-first.
- G4. The fourteen roles ship as plugin agents, each preloading its skills, with the shared operating rules factored into one skill.
- G5. The fourteen vetted third-party skills ship inside the core plugin with their LAB OVERLAY, `PROVENANCE.md` and upstream `LICENSE`, with the Claude-Science-only overlay items removed.
- G6. `initializing-a-research-lab` scaffolds a project-local lab (record folders, templates, artifact store, memory store, standing rules in the project `CLAUDE.md`, connector configuration, LFS and ignore rules) in any project folder, and never touches a global user setting.
- G7. `migrating-from-claude-science` imports a Claude Science project into that scaffold: memories, profiles (as a diff against the shipped agents), every artifact version with its dependencies and reviewer verdicts, a where-we-left-off digest, the connector list and the secret names. It reads a copy of the database, never the live file, and never reads encrypted tables.
- G8. Artifacts follow Claude Science's own model (workspace is scratch; `save` promotes a file to a full-copy version; `version_of` chains versions; inputs, producing role and producing command are recorded; markers `{{artifact:VID}}` reference versions; discovery goes through the store), implemented as a git-committed store with a stdlib Python script, with Git LFS for files above a threshold.
- G9. Memory follows Claude Science's model (entity scopes `profile`, `project`, `artifact`, a session scratchpad; evidence tags `stated`/`observed`/`inferred`; the "what not to save" rules) with ultrapowers' mechanics (one fact per file in git, an index with a hard line budget, a four-criteria gate, a lint script, a nudge hook and a post-compaction rescue hook), and keeps the role that learned each fact.
- G10. `init` offers every connector the Claude Science profiles had that has a Claude Code equivalent, plus the science connectors on the owner's claude.ai account, and writes the ticked ones to the project `.mcp.json` with credentials as environment-variable references.

Non-goals: what is left out on purpose, and where it goes instead.

- Other harnesses (Codex, Cursor, Gemini, Pi, OpenCode, Kimi, Muse, Hermes, Antigravity, Devin). They stay in `obra/superpowers`; the hand-ported `.codex/agents/*.toml` in the source project repo is untouched.
- ultrapowers' ticket engine, autopilot, QA lanes, vulnerability hunt and guardrail hooks. They stay in ultrapowers.
- Claude Science's 20 `bundled:*` bio MCP servers (biomart, literature, chemistry, zinc, …). They exist only inside Claude Science; the migration report lists them as not portable.
- Skills that reach Claude Code through the user's claude.ai account: the claude.ai-synced skills (`built-in-browser`, `chrome-browser`, `computer-use`, `code-quality-audit`, `codebase-mastery`, `deep-research`, `doc-coauthoring`, `docs`, `documentation-researcher`, `google-workspace`, `import-memory`, `learn`, `mcp-server-builder`, `morning`, `web-artifacts-builder`) and the Anthropic example skills (`algorithmic-art`, `brand-guidelines`, `canvas-design`, `internal-comms`, `mcp-builder`, `theme-factory`). Claude Code lists them as `anthropic-skills:*` and `example-skills:*` when the account is signed in, so the plugin does not vendor them; the migration's profile diff names them by class.
- Claude Science's compute providers (SSH, Modal, managed model endpoints), its sandbox and per-session kernels, its deny-by-default network, its org policy and its auto-mode classifier. Claude Code has its own permission modes and sandboxing; the project brief names the project's environment (§5), and the migration reports the grants and domains as a checklist (D11).
- Claude Science's helper agents (Onboarding, Uploads, Bookmarker). Uploads become artifact versions with `destination: upload`; the other two have no lab function.
- Loading Claude Science transcripts into agent context. The migration can export them as a searchable archive; no skill reads them automatically.
- Re-vetting the 14 third-party skills or adding new ones. The vetting records in `09_skill_vetting/` stand.
- Rewriting the source project's `research_lab/` records. The migration adds to that folder; it edits nothing that exists.

Anti-goals: what would make this a failure even if it works.

- A lab that only works for the source project: any hardcoded drive-letter path, data-task id, dataset name or decision id inside a plugin skill or agent.
- A migration that loses provenance: artifacts imported as latest bytes only, or memories imported without their evidence tag and learning role.
- A skill rewrite that changes behaviour silently: a lab rule reworded into the superpowers form without a pressure test showing the new wording still holds.
- Secrets in the repo or the plugin: any key value, token or encrypted blob copied out of Claude Science.
- A plugin that edits global user configuration (`~/.claude/settings.json`, user memory) during `init` or `migrate`.

## Constraints

Project-wide requirements that bind every task:

- Plugin and marketplace name `science-ultrapowers`; repository `raoofaltaher/science-ultrapowers`, public, default branch `main`; version `0.1.0` in `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (`plugins[0].source` = `"./"`), kept in sync by `.version-bump.json` and `scripts/bump-version.sh`. Evidence: superpowers `.version-bump.json`; Claude Code marketplace reference (`"./"` source, `version` drives updates).
- Licence: the Ultrapowers-style proprietary, source-available licence (`LICENSE`); third-party portions keep their licences (superpowers v7.0.2 under MIT, credited in the README as the template, and the fourteen vendored skills, each with its upstream `LICENSE`). Evidence: superpowers `LICENSE`; `PROVENANCE.md` files.
- Zero runtime dependencies beyond: bash (Git for Windows on Windows), node (for the lint script, as in ultrapowers) and Python 3.11+ standard library (for `verify_doi.py`, `jev_ask.py`, `artifacts.py`, `migrate_claude_science.py`). No pip packages in the core plugin. The figure/poster third-party skills keep their documented separate environment (`.venv-lab-skills`). Evidence: superpowers `AGENTS.md` (zero-dependency); `INSTALL.md` of the current team.
- Skill writing follows `skills/writing-skills/SKILL.md` and `references/discovery.md`: `description` starts with "Use when", third person, triggers only, no workflow summary; skill names are letters, digits and hyphens, verb-first; skills name actions, never tool names; cross-references as `science-ultrapowers:<skill>`, never `@` links; frequently loaded skills under 200 words, others under 500 where possible (the discipline and orchestration skills are exempt from the budget); scripts invoked through their interpreter (`python "${CLAUDE_PLUGIN_ROOT}/skills/<skill>/scripts/x.py"`). Evidence: `skills/writing-skills/SKILL.md`, `references/discovery.md`.
- The bootstrap (`using-science-ultrapowers` body plus the hook's wrapper) stays under 9,000 characters: hook-injected context is capped at 10,000. Evidence: Claude Code hooks reference, "Injecting context".
- Plugin agents use only the supported frontmatter (`name`, `description`, `model`, `tools`, `disallowedTools`, `skills` up to 32, `color`); `initialPrompt` and `permissionMode` are ignored in plugin agents and are not used. Agent names contain no `:`. Evidence: Claude Code plugin components reference, sub-agents reference.
- No `CLAUDE.md` at the plugin root carries instructions (it is not loaded); all instructions live in skills. Evidence: plugin manifest reference, "Standard layout".
- `${CLAUDE_PLUGIN_ROOT}` is used for reading plugin files only; nothing is written there. Project state lives in the project. Evidence: plugin manifest reference, "Environment variables".
- The plugin repository itself uses no Git LFS (Claude Code never fetches LFS content when installing a plugin). LFS applies to project repositories only. Evidence: Claude Code host-marketplace reference, "Keep plugin files out of Git LFS".
- `init` writes permission rules only into the project's `.claude/settings.json`, only on `--permissions`, and only when that file does not exist; the migration writes grants and domains as a checklist, never into a settings file (D11).
- Every rule that is project-specific (paths, current priorities, decision ids) lives in the project: `research_lab/00_project_knowledge/PROJECT_BRIEF.md`, the project `CLAUDE.md`, `research_lab/lab.json`. The sorting rule for the current fifteen `CLAUDE.md` rules and `research-lab-workflow` §2c: a rule is lab law (goes into a plugin skill, without its decision id) unless it names a project artifact, path, person or id. Under that rule the evidence rule with attribution-only preprint citations, re-checking at every level, numbers from the ledger, the gates, the test-split rule, access requests through the human specialist, Jev's positioning, verification claims naming the check and environment changes needing approval, session kickoff and stand-up, scratch files outside tracked folders, and the devil's-advocate gate are lab law; the Tier-B approvals, `<a funder folder>`, the `.github` legacy agents, the `uv` dev commands and the critical-path lines stay in the source project's `CLAUDE.md` and brief. Evidence: anti-goal 1; `claude_code_team/CLAUDE.md`; `research-lab-workflow/SKILL.md` §2c; My call on the sorting rule.
- Record folder layout of the project lab is the current one, unchanged: `00_project_knowledge` … `09_skill_vetting`, `templates/`; two folders are added: `artifacts/` and `memory/`; one git-ignored folder `.scratch/`. Evidence: `research_lab/README.md` map.
- Windows is a first-class host: hooks run through `hooks/run-hook.cmd`; scripts use `python` (or `uv run python`) and forward slashes; nothing requires WSL. Evidence: superpowers `hooks/run-hook.cmd`; the lab's `INSTALL.md`.
- The migration never opens the live `operon-cli.db`; it copies it (and `-wal`/`-shm` if present) and opens the copy read-only with `immutable=1`. It refuses to run while Claude Science is running (a `claude-science` process, or a live pid in the config home's `auth-owner.lock`) unless `--allow-running` says the data directory is a copy no application writes to, because a database copied mid-write can be corrupt. It never queries `user_secrets`, `oauth_tokens`, `anthropic_api_keys`, `cloud_credentials`, `package_mirror_credentials`; it reads `user_secrets.name` only through a name-only projection. Evidence: Claude Science `self-awareness` skill (denied tables); `operon-cli.db` mtime during this session.

## Decision record

### D1: Fork superpowers, cut to Claude Code, lab as skills + agents + init + migrate, artifacts and memory as git-committed stores

- **Chosen:** clone `obra/superpowers` v7.0.2, remove `.git`, re-initialise; delete non-Claude-Code harness files; rewrite the lab skills in superpowers form; add `using-science-ultrapowers`, `initializing-a-research-lab`, `migrating-from-claude-science`, `saving-artifacts`, `remembering-for-the-lab`, `holding-lab-meetings`, `searching-the-literature`, `planning-paper-figures`; ship 14 role agents and the 14 vetted skills; project-local stores for artifacts and memory committed to git.
- **Why this one:** it is the only option that meets all three constraints the owner set: the superpowers repository as the exact template, his own setup carried over, and a migration that resumes the Claude Science state. Evidence: the owner's messages in this conversation (2026-11-07); superpowers `docs/porting-to-a-new-harness.md` (skills + bootstrap are the whole integration); `orgs/<org>/operon-cli.db` row counts (`memories` 79, `user_agents` 15, `artifacts` 418, `artifact_versions` 555, `artifact_dependencies` 940, `verification_checks` 1,527).
- **Rejected:** reimplementation from scratch (the K-Dense route), because the owner asked for the superpowers repository itself and a reimplementation discards its tested bootstrap, Windows wrapper and version tooling. Evidence: the owner's request; superpowers `AGENTS.md` ("carefully-tuned content").
- **Rejected:** packaging `claude_code_team/` as-is, because it keeps source-project paths and Claude Science overlay snippets, has no init or migrate, and its skills are not in superpowers form. Evidence: `claude_code_team/CLAUDE.md` rule 1; snippets that call the host object's skill reader in 11 overlays.
- **Rejected:** a science mode inside ultrapowers, because the owner said not to reach ultrapowers' maturity, and its ticket engine, QA lanes and guardrails would come along. Evidence: the owner's request; `ultrapowers/skills` (31 skills).
- **Failure points:** (1) rewriting lab text into superpowers form changes behaviour; mitigation: no rewritten discipline skill ships without a baseline-versus-skill pressure test (writing-skills Iron Law). Evidence: `skills/writing-skills/SKILL.md`. (2) Subagents cannot ask the user or message each other; mitigation: orchestrator-routed hand-offs, as the current hand-off block already encodes, with `ACCESS REQUEST` / `APPROVAL NEEDED` blocks relayed by the main session. Evidence: `research-lab-workflow/SKILL.md` §9; sub-agents reference ("AskUserQuestion is removed from subagents"). (3) Large binaries in git; mitigation: D4. (4) Live database; mitigation: copy-then-read (Constraints). (5) Profiles reference Claude Science bundled skills; mitigation: D7 mapping.
- **Edge cases:** no Claude Science data dir on the machine: `init` runs alone and never offers `migrate`. Several projects in the database (three exist: `proj_example`, `Getting started`, the source project): `migrate` lists them and asks. Data dir moved (`config.toml data_dir` = `<data-dir>`, `last_move_from` = the `C:` copy): `migrate` reads `config.toml` first and warns when two dirs exist, preferring `data_dir`. A profile edited in Claude Science after the agent files were generated: `migrate` writes a diff report and changes no agent. Evidence: `projects` table; `config.toml`; `last-data-dir-move.json`.

The main Claude Code session is the orchestrator: when the user addresses the team, `running-the-lab` has it act as the Research Project Manager (brief, dispatch, relay, record); `claude --agent science-ultrapowers:lab-project-manager` remains possible.

### D3: Claude Science's artifact model, as a git-committed store with a script

- **Chosen:** `research_lab/artifacts/` holding `store/<artifact_id>/v<NNN>_<filename>` (full copy per version) and four JSONL ledgers mirroring the Claude Science tables field for field: `artifacts.jsonl` (id, filename, latest_version_id, folder, is_user_upload, is_ephemeral, superseded_by, retention, destination), `versions.jsonl` (id, artifact_id, version_number, parent_version_id, kind = `copy` | `link`, content_type, size_bytes, sha256, storage_path, agent_name, producing_command, producing_session, code_description, is_intermediate, is_checkpoint, destination, environment, created_at, source = `claude-science` | `lab`, status = `ok` | `missing` | `replaced` | `changed`; `destination` is recorded per version, so a `working_data` save replaces only earlier `working_data` copies and a `snapshot` milestone inside a `working_data` artifact is kept), `dependencies.jsonl` (version_id, depends_on_version_id, reference_name), `verification_checks.jsonl` (id, version_id, claim, verdict, severity, evidence, rebuttal, reviewer_role, status, resolution, created_at). The script `skills/saving-artifacts/scripts/artifacts.py` offers `save`, `search`, `path`, `lineage`, `graph`, `link`, `check` (`add`, `list`, `review`), `mark-addressed`, `resolve` (markers to relative links) and `lfs-check`. Markers are `{{artifact:VID}}` and `{{artifact:art_<ID>}}` as in Claude Science; `resolve` turns a bare marker into a link and a marker written as a link destination, `[text]({{artifact:VID}})`, into its target. Imported rows keep their Claude Science UUIDs; new rows get UUID4 ids; `resolve`, `path` and `lineage` accept both, and a unique prefix of at least 6 characters stands for the full id.
- **Why this one:** the owner asked for Claude Science's exact artifact methodology plus git; the JSONL mirror lets a migrated row and a new row share one schema, and git gives history on top. Evidence: Claude Science system prompt "Working style" (`save_artifacts`, `version_of`, `environment`, `checkpoints`, `destination`), "The host Object" (its artifacts and lineage calls, its lineage graph, markers); `self-awareness` skill table list; the owner's answer "ALL, it must be also a git included".
- **Rejected:** git history alone with a manifest, because Claude Science keeps a full copy per version and the owner wants that model as well as git. Evidence: the owner's answer.
- **Rejected:** a SQLite database in the repo, because binary database files do not diff or merge in git and the roles would need a query tool for every read; JSONL is greppable by the roles directly. Evidence: My call.
- **Failure points:** two roles saving at once corrupt a JSONL line; mitigation: only the orchestrator runs `save` (subagents return files and a hand-off block; the orchestrator saves), and `save` appends atomically (write temp, rename). Evidence: My call. Dependency extraction in Claude Science is automatic; here it is not; mitigation: the hand-off block carries `Inputs:` (artifact ids or paths) and `save --inputs` records them; missing inputs are recorded as an empty list, never guessed. Evidence: Claude Science system prompt ("dependency edges land asynchronously"); `research-lab-workflow` §4.
- **Edge cases:** a repo file saved as an artifact (the 191 `Code/…` rows): `link` records path + sha256 without copying; `path` returns the repo path. A file above the LFS threshold: D4. A `working_data` destination: only the latest working copy is kept, as in Claude Science; the destination is set when the artifact is created and later saves inherit it. An artifact's identity is its project-relative path: saving the same path again adds a version to the same artifact. Evidence: `artifacts` rows with `storage_path` beginning `~/<drive>:/`; Claude Science "Checkpoint Rule".

### D4: Git LFS above an exact size threshold, one `.gitattributes` line per file, in project repositories only

- **Chosen:** `init` writes `research_lab/artifacts/.gitattributes` with a header comment and two rules, `store/** -text` (stored copies stay byte-exact, so the recorded sha256 holds) and `*.jsonl text eol=lf`; `save` and `migrate` restore either rule in an existing file. `save` and `migrate` append one exact-path line (`store/<artifact_id>/v<NNN>_<name> filter=lfs diff=lfs merge=lfs -text`; `store/<artifact_id>/v<NNN>_*` when the name holds whitespace or glob characters) for every stored file whose size is at or above the threshold (10 MB, `lab.json` `lfs.thresholdMB`), before the file is staged; `link` stores nothing and writes no line, and a replaced `working_data` copy loses its line. `migrate` writes all its lines before the first commit of the imported store. `artifacts.py lfs-check` lists stored files over the threshold without a line, the LFS total, the line count and whether the git-lfs filter is configured, and exits non-zero on a missing line, or on an unconfigured filter while LFS lines exist; `save` and `migrate` print a budget warning when the LFS total passes 800 MB (`lab.json` `lfs.budgetWarnMB`).
- **Why this one:** the owner chose an exact threshold; `.gitattributes` cannot filter by size, but git honours exact-path attribute lines, so per-file lines implement the threshold exactly and keep small PDFs and CSVs in plain git. The source project repository has a GitHub remote (`<owner>/<project-repo>`), git-lfs 3.8 installed and a 705 MB `.git`, so the quota matters. Evidence: the owner's MCQ answers (LFS above a threshold; exact threshold, per-file lines); `git remote -v`, `git lfs version`, `du -sh .git` run in this session; GitHub free LFS quota 1 GB storage / 1 GB bandwidth per month (GitHub documentation, Not confirmed this session).
- **Rejected:** an extension list regardless of size, because it spends LFS quota on small files. Evidence: the owner's answer. Rejected: pointer records only, because the bytes would not be in git. Evidence: the owner's earlier answer. Rejected: committing everything plain, because the source project's store already holds a 92 MB zip and model checkpoints. Evidence: `artifacts-2-11-2026.zip` listing (`T-083_fulltext_pdfs.zip` 92,030,931 bytes); `best_model.pth.tar` rows.
- **Failure points:** LFS not installed; mitigation: `init` checks `git lfs version` and, when absent, still writes the lines and reports the install step as a user action. LFS installed but its filter never configured (`git lfs install` not run): git honours the attribute line for `check-attr` yet stores plain bytes; mitigation: `save` checks `git config --get filter.lfs.clean` and warns per tracked file, and `lfs-check` fails. Evidence: the PLAN-02 final review reproduced it on this machine. A worktree created by Claude Code holds pointer files; mitigation: `path` reports a pointer (size differs from the record and the file starts with the LFS spec line) as status `pointer` with a `git lfs pull` hint, and `saving-artifacts` says the same. Evidence: Claude Code worktrees reference. A file staged before its line is written would enter plain git; mitigation: `save` writes the line, then stages, in that order, and `lfs-check` is part of the stand-up. Evidence: My call.
- **Edge cases:** the plugin repository must not use LFS at all (Constraints). A stored file edited in place to grow past the threshold: impossible, versions are immutable; a new version gets its own line. The `.gitattributes` grows by one line per large version; at 1,000 lines `lfs-check` suggests folding into a per-artifact pattern (`store/<artifact_id>/** filter=lfs diff=lfs merge=lfs -text`), which the script then honours as covering every version of that artifact. Evidence: My call.

### D5: Memory: Claude Science model with ultrapowers mechanics, role kept

- **Chosen:** `research_lab/memory/` with `MEMORY.md` (index, hard budget 150 lines, default from `lab.json`), one fact per file under `project/` and `artifact/<artifact_id>/`, frontmatter `name`, `description`, `metadata: {type: gotcha|decision|lesson|directive|vocabulary, entity: project|artifact:<id>, evidence: stated|observed|inferred, learned_by: <role>, origin: agent|extractor|user|import}`, `date`. Profile-scope facts (about the owner) are not stored in the project; the skill points them at Claude Code's own user memory. The session scratchpad is `research_lab/.scratch/<date>-<session>/<role>.md`, git-ignored, deleted by the stand-up skill. The four-criteria gate (verified, durable, expensive, not derivable), the "what not to save" list (records, artifacts, code, fix recipes, task state, tool availability, third-party personal data, anything in `CLAUDE.md`), the lint script (`skills/remembering-for-the-lab/scripts/memory-lint.mjs`, ported from ultrapowers), the `Memory-Ref` commit trailer, a UserPromptSubmit nudge and a SessionStart(compact) rescue hook. Sub-agents propose memories in their hand-off block; the orchestrator gates and writes them; the kickoff reads the index, the stand-up is the gating moment. `search before acting`: `running-the-lab` has the orchestrator grep the memory store before dispatching a role.
- **Why this one:** the owner chose this combination; Claude Science's scopes and evidence tags are the model its 79 rows already follow, and ultrapowers' mechanics are the git-native version he already runs. Evidence: the owner's MCQ answer; Claude Science system prompt "Memory"; `ultrapowers/skills/team-memory/SKILL.md`; `memories` table columns.
- **Rejected:** per-role memory files, because Claude Science keeps one pool per user and the role is only attribution; a `learned_by` field gives the attribution without splitting the pool. Evidence: `memories` schema (no agent column; `source_frame_id` → `frames.agent_name`).
- **Rejected:** storing decisions and findings in memory, because they are lab records already. Evidence: Claude Science "What NOT to save" ("the DB is authoritative"); `findings-ledger/SKILL.md`.
- **Failure points:** the index budget overflows after import (79 rows, many long); mitigation: `migrate` writes the imported rows as files and an index with one line each, then runs lint and, if over budget, marks the oldest `inferred` rows for the owner's prune rather than dropping any. ## Architecture

Units, each with one purpose:

1. **Plugin shell** (the superpowers skeleton): `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `hooks/hooks.json`, `hooks/run-hook.cmd`, `hooks/session-start`, `hooks/memory-nudge`, `hooks/memory-postcompact`, `hooks/lib/`, `.version-bump.json`, `scripts/bump-version.sh`, `scripts/lint-shell.sh`, `README.md`, `LICENSE`, `RELEASE-NOTES.md`, `AGENTS.md` (contributor rules), `docs/`, `tests/`.
2. **Bootstrap**: `skills/using-science-ultrapowers/SKILL.md`, injected at SessionStart (startup, clear, compact). Teaches: skills exist, invoke before acting, the lab's three standing laws in one line each (evidence rule, records are the truth, nobody reviews their own work), how the team is addressed, and that the project `research_lab/` is the lab when present.
3. **Lab skills** (`skills/`): `running-the-lab`, `holding-lab-meetings`, `verifying-evidence-by-doi` (+ `scripts/verify_doi.py`, tests), `recording-findings`, `requesting-reference-access`, `deciding-with-jev` (+ `scripts/jev_ask.py`), `searching-the-literature`, `planning-paper-figures`, `saving-artifacts` (+ `scripts/artifacts.py`), `remembering-for-the-lab` (+ `scripts/memory-lint.mjs`), `initializing-a-research-lab` (+ `templates/`, `connectors.json`, `scripts/init_lab.py`), `migrating-from-claude-science` (+ `scripts/migrate_claude_science.py`).
4. **Kept superpowers skills**: `writing-skills`, `test-driven-development`, `systematic-debugging`, `verification-before-completion`, `requesting-code-review`, `receiving-code-review`, `dispatching-parallel-agents`.
5. **Vetted third-party skills**: the 14 plus `typesafe-ai`.
6. **Agents** (`agents/`): 14 role files.
7. **Project lab** (created by `init` in a project): `research_lab/` with records, `templates/`, `artifacts/`, `memory/`, `.scratch/`, `lab.json`, `README.md`; `references/` for full-text PDFs (git-ignored by default); project `CLAUDE.md` section; `.mcp.json`; `.gitattributes`; `.gitignore` lines.

How they talk: the bootstrap and `running-the-lab` are the only things the main session must know; everything else is reached by skill name. Agents receive a task brief (running-the-lab §3) and return a hand-off block (§4) whose fields feed `saving-artifacts` (deliverables, inputs), `recording-findings` (F-ids), `requesting-reference-access` (REQ-ids) and `remembering-for-the-lab` (memories proposed). Scripts read and write only under the project `research_lab/`.

## Data flow

Enters: user messages; project files; Claude Science data dir (read-only, copied); Crossref/OpenAlex/connector responses; TypeSafe API responses.

Leaves: nothing leaves the machine except Crossref/OpenAlex queries (DOIs, titles), connector queries, and Jev calls (policy-filtered, redacted, logged, as today).

Stored, and where: lab records in `research_lab/*`; artifact bytes in `research_lab/artifacts/store/` (LFS above threshold); artifact ledgers as JSONL; memory as Markdown files plus index; session scratch in `research_lab/.scratch/` (not committed); `JEV_CALLS.jsonl`; migration outputs under `research_lab/migration/`. All committed by the orchestrator under D10 (`research_lab/` only) with the hand-off's commit message and the `Memory-Ref` trailer when a memory was written.

Trust boundaries: Claude Science database content, PDFs, web pages and connector results are untrusted data (never instructions); the migration treats every text field as data and writes it into fenced blocks; `jev_ask.py` wraps untrusted text as today. Secrets never cross: the migration projects `name` only; `.mcp.json` carries `${VAR}` references only.

## Error handling

- `migrate` cannot find a data dir or the project: stops with the paths it tried; writes nothing.
- The database is locked or the copy fails: stops; reports the mtime and advises closing Claude Science or retrying; never opens the live file.
- An artifact file named in a version is missing on disk: a ledger row with `status: missing` and a line in the report; the run continues.
- A repo-linked artifact's checksum differs from the stored one: `status: changed`, both hashes in the report.
- `save` on a file outside the project, or on a path that already has a version with the same sha256: refused with the reason (the second case suggests `--version-of` or no-op).
- `save` on a file at or above the LFS threshold: writes the exact-path `.gitattributes` line before staging the file (D4) and warns when the git-lfs filter is not configured.
- LFS not installed: `init` and `save` report it as a user action; nothing silent.
- Memory index over budget: the write is refused and prune is proposed (ultrapowers rule).
- A hook runs in a folder without `research_lab/memory/`: exits 0 silently.
- A subagent returns without a hand-off block: the orchestrator treats the task as not delivered and says so (running-the-lab rule).
- `verify_doi.py` network failure: `ERROR` status, never `VERIFIED`; exit 1. A retraction check that cannot run: `ERROR`, never a pass.
- Jev key absent: `deciding-with-jev` says so and the specialist decides; nothing is logged as an answer.
