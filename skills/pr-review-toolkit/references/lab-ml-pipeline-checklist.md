# Lab ML-pipeline review checklist (lab overlay, lab-authored)

Added because the upstream lenses do not name the defect classes that ML pipelines have shown. Apply it under the `code` and `types` lenses to every change under `src/`, `config/` or the train, evaluate, test, predict and calibration entry points. A violated item is a blocking finding at gate G3.

1. **Cross-entrypoint construction parity.** Every entry point builds the model, text/image preprocessing and data pipeline through the same factory and config path; no script constructs components directly. Typical defect: a factory bypass in the evaluation scripts.
2. **Reproducibility and seeding.** Every entry point calls `set_seed` with the configured seed before building data or models; a determinism setting that cannot be honoured raises an error instead of degrading to a warning; seed, commit and config hash are recorded in the experiment register. Typical defects: a test script without `set_seed`; soft-enforced determinism.
3. **Config-schema hygiene.** No orphaned or unconsumed keys; no silent runtime override of a validated value; a changed default is a documented change. Before calling a key dead, trace every read of it: a key read unconditionally by a loader (a plain dict subscript on every split load) is not dead even when its downstream value is currently unreachable, and removing it would raise `KeyError`. Typical defects: a dead key; a config value silently overridden at runtime.
4. **Validator and factory parity.** Every value the config validator accepts is implemented by the factory, and every implemented option is accepted by the validator. Typical defect: an optimizer accepted by the config validator but not implemented in the factory.
5. **Metric and result serialisation.** Metric names and prefixes match their split and task; a validation metric is never written under a `train_` key; every number that reaches a document is traceable to a ledger entry. Typical defect: per-task validation values stored under `train_*` columns.
6. **Split discipline and leakage.** The test split is read only by a pre-registered final evaluation; any change to splitting or deduplication re-runs the sample-ID overlap check across splits. Typical defect: sample-ID overlap across splits.
